# 管理端（服务端网页）设计

> 状态：设计已定，尚未实现。后端的管理员身份、RBAC 与审计在 P1 已经落地（见
> `docs/identity-and-admin.md`），本文档定的是**网页本体**：有哪些页面、谁能进、
> 以及「管理员不许看用户正文」这条红线用什么机制保证——而不是靠人记得。

## 0. 现状盘点

已有：

- 管理员身份体系：`app/admin/`（Argon2id 密码 + Fernet 加密的 TOTP、锁定、会话撤销）。
- RBAC：`app/admin/rbac.py` 里 13 个权限、5 个系统角色，由代码版本控制、启动时幂等写入。
- 审计表：`admin_audit_events`（append-only，不存原始 IP/UA，只存哈希）。
- 双平面隔离：用户令牌 `it_at_`、管理员令牌 `it_admin_at_`，中间件按路由前缀分别验证。

没有：

- 任何 HTML。整个后端没有 `templates/`、没有 `static/`，只在开发环境挂 `/docs`。
- `/admin/v1` 下只有 4 个端点：`auth/login`、`auth/me`、`auth/logout`、`audit-events`。
- **任何守着红线的测试**。`tests/test_admin_auth.py` 只有 2 个用例（平面隔离、analyst
  读不到审计），红线目前是一句写在文档里的话。

## 1. 一条红线

> **管理端的任何页面、任何 API 响应、任何日志、任何导出产物，都不得呈现用户创作的正文。**

正文指：聊天原文、生活记录的文字与图片、语音与其转写、记忆 claim 的文本、原始证据、
备忘内容。也就是 `raw_ledger`、`working`、`episodic`、`semantic`、`procedural`、
`memos`、`insights`、`media_assets`、`moment_interactions`、`memory_claims`、
`memory_evidence`、`memory_revisions`、`user_events` 这些表里的内容列。

**这不是合规要求，是产品要求。** 这个产品的立身之本是「智能体是用户在 app 里唯一的
倾听者」，生活区是宣泄而不是社交。只要后台存在一个「点开这个用户看他写了什么」的入口，
这句话就不再是真的——不管那个入口有没有被用过。红线因此比常规后台严格一档：不是
「有权限才能看」，而是**没有任何角色能看，连 super_admin 也不能**。

推论（三条同样强的规则）：

1. **不许枚举用户。** 管理端没有「用户列表」页。要查一个账号只能输入精确的 user_id，
   而且每次查询写审计事件。列表页是漫游的入口，漫游是红线的慢性泄漏。
2. **不许人工代劳。** 「用户申请导出数据」这类场景不能靠管理员去读一遍再发给他。
   见 §3 的工单设计：产物由后台任务直接生成并投递，不经过管理员的眼睛。
3. **唯一的例外必须被单独设计。** 危机干预命中的样本需要人复核，这是全系统唯一
   一个人可能看到用户话的地方。它走脱敏管道，且必须让用户知道（§4 的 B3）。

## 2. 红线怎么落到代码

四层，从外到内。只有第 2 层是真正的闸门，其余三层是让违反变得难以悄悄发生。

### 2.1 权限层（已有，补守卫）

`rbac.py` 的权限名里没有任何一个授予读正文——`privacy.read` 写着「不含用户正文」，
`account.status.read` 写着「不含内容」，`safety.read` 写着「匿名化」。

要补的守卫：一个测试断言 `PERMISSIONS` 的键集合与文档里的清单逐字相等。新增权限时
测试变红，迫使新增者回来读这一节。**光靠命名不是保证，命名只是让意图无处可躲。**

### 2.2 数据闸门（新建，这是真正的机制）

新建 `app/admin/dataplane.py`，向管理平面只提供一种数据库会话：

```python
USER_CONTENT_TABLES: frozenset[str] = frozenset({...})  # §1 列出的那些表

def admin_session(...) -> Session:
    """给 /admin/v1 用的会话。碰到用户内容表就抛 AdminDataPlaneViolation。"""
```

实现用 SQLAlchemy 的 `before_cursor_execute` 事件：编译后的 SQL 一旦出现
`USER_CONTENT_TABLES` 里的表名就抛异常。**管理端不是靠人记得不查，是查了就报错。**

聚合数字怎么办？聚合不能绕过闸门（`SELECT count(*) FROM episodic` 一样会被拦）。
所以指标走**独立的聚合表**：worker 定时把计数、分布、成功率写进
`metrics_daily` 之类的新表，管理平面只读这张表。代价是指标有延迟（分钟级到小时级），
收益是管理平面在数据库层面根本接触不到用户内容——延迟是可以接受的，
后台看的是趋势，不是实时。

生产环境再加一层：给管理平面配独立的 PostgreSQL 角色，对用户内容表不授予 SELECT。
数据库拒绝比应用层拒绝更硬，应用层那层留着是为了让 SQLite 开发环境和测试也能验。

### 2.3 响应层

`/admin/v1` 下所有响应模型的字段类型受限：`int` / `float` / `bool` / 时间戳 /
`Literal` 枚举 / 以及显式登记的短字符串（user_id、状态码、管理员名、配置键）。
**不允许出现未登记的自由 `str` 字段**——一个测试遍历所有 admin 路由的
`response_model`，递归检查字段类型，遇到未登记的 `str` 就红。

这层挡的是「有人为了方便，把一段用户文本塞进了某个 `note` 字段」。

### 2.4 审计层

`/admin/v1` 下除 `auth/*` 之外的每一个请求都写 `admin_audit_events`；一个测试遍历
路由表，断言每个路由都挂了审计依赖。按 user_id 的查询额外把 user_id 写进
`resource_id`（审计需要可追溯），但 `metadata_json` 里不许出现内容。

## 3. 页面清单

分两批。批次 A 完全不接触用户数据，先做；批次 B 触及账号但仍不看正文，且需要先把
§2.2 的闸门和 §4 的脱敏管道做完。

### 批次 A：运维面板

| # | 页面 | 权限 | 内容 | 数据来源 |
|---|---|---|---|---|
| A1 | 登录 | 公开 | 用户名 + 密码 + TOTP；锁定提示 | `POST /admin/v1/auth/login` |
| A2 | 总览 | `metrics.read` | DAU/WAU、新增、留存曲线、四入口使用分布、当日 LLM/ASR 调用量与成本 | 聚合表 |
| A3 | 任务与队列 | `jobs.read` / `jobs.retry` | `outbox_events` 积压与死信数、worker 心跳（`app/worker/healthcheck.py`）、按错误类型分组、重试按钮 | 聚合表 + worker 心跳文件 |
| A4 | 记忆质量 | `metrics.read` | 抽取成功率、`memory_claims` 按 status 分布、改写率、检索命中率与召回延迟分位 | 聚合表 |
| A5 | 配置与灰度 | `config.read` / `config.write` / `config.publish` | prompt 版本、模型路由、功能开关、灰度比例；草稿 → 发布 → 回滚三态，紧急停用单独按钮 | 新建配置表 |
| A6 | 服务健康 | `metrics.read` | `/health`、`/ready`、DB 连接、dashscope provider 错误率与延迟分位 | 实时探测 + 聚合表 |
| A7 | 审计日志 | `audit.read` | `admin_audit_events` 游标分页、按 action/outcome/actor 过滤 | `GET /admin/v1/audit-events`（已有） |
| A8 | 管理员管理 | `admin.manage` | 管理员列表、角色分配、会话撤销、锁定状态；不显示 TOTP secret | 新建端点 |

### 批次 B：触及账号，仍不看正文

| # | 页面 | 权限 | 内容 | 红线约束 |
|---|---|---|---|---|
| B1 | 账号状态 | `account.status.read` / `.write` | 按精确 user_id 查：状态（活跃/封禁/注销中）、注册时间、最后活跃、设备会话数、封禁与恢复 | 无用户列表页；无任何内容字段；每次查询写审计 |
| B2 | 隐私工单 | `privacy.read` / `privacy.execute` | 导出/删除工单列表与状态机、批准与执行、失败重试 | 只显示状态与时间戳，不显示产物；产物由任务直接投递给用户 |
| B3 | 安全审核 | `safety.read` / `safety.write` | 脱敏后的危机命中片段队列、策略草稿与发布 | 见 §4 |

### 不做的页面

- **用户列表 / 用户详情浏览**：红线推论 1。
- **聊天记录查看器**：红线本体。
- **「以用户身份登录」（impersonation）**：这是红线的完全绕过，永久不做。
- **记忆内容编辑器**：记忆是用户的，不是运营的。记忆的错误由用户在 app 内纠正
  （`memory_revisions` 已经支持），不由后台改。

## 4. 唯一的例外：危机命中样本

危机干预规则命中的内容需要人复核策略是否合适，否则策略永远无法改进。这是全系统
唯一一个人可能读到用户话的地方，所以它单独设计：

1. **脱敏管道**：只保留命中的那一个片段（不是整段对话），去掉人名/地名/联系方式，
   user_id 只以哈希出现。脱敏在写入审核队列时完成，队列表里存的就是脱敏后的文本。
2. **审核队列是独立表**，不在 `USER_CONTENT_TABLES` 里——因为它存的已经不是用户正文，
   是脱敏样本。这个豁免必须在代码里显式写明理由。
3. **保留期**：样本有明确的过期时间（建议 30 天），到期硬删除。
4. **用户可知**：产品文案里必须说明「触发安全策略的内容会被脱敏后用于改进安全策略」。
   做不到告知，就不做这个队列——宁可让安全策略靠合成样本改进。

这一条是产品与安全的取舍，需要单独定案，不随批次 A 一起做。

## 5. 技术选型

**FastAPI + Jinja2 服务端渲染 + 少量原生 JS。不引入前端框架和构建链。**

理由：

- 使用者只有内部少数几人，SPA 的构建流水线、状态管理、鉴权同步都是净成本。
- **令牌安全**：SPA 需要把管理员令牌放进浏览器可读的地方，一次 XSS 就失守；SSR 可以
  用 `HttpOnly` + `Secure` + `SameSite=Strict` cookie，配合 CSRF token 保护表单。
  管理端的失守代价远高于用户端，这一项本身就足以定选型。
- 部署不用第二条流水线，与现有 docker-compose 一致。

代价（明写，不假装没有）：交互不如 SPA 顺滑；图表要用轻量方案（内联 SVG，或按需引
一个单文件图表库），不上 ECharts 那种体量；表格排序筛选走 URL 查询参数而不是前端状态。

需要新增的机制：

- 管理员会话除 Bearer 之外接受 cookie（当前中间件只认 `Authorization` 头）。
  cookie 与 Bearer 共用同一张 `admin_sessions` 表和同一套校验，只是取令牌的位置不同。
- CSRF：所有改状态的表单带一次性 token，绑定管理员会话。
- 严格 CSP：`default-src 'self'`，禁 inline script（模板里不写 `onclick`）。

**管理端不套用 `内在地形-美学基线-v1.md`。** 那套律（七档不透明度、三档圆角、
两个功能色、丝滑缓动）是为「内在地形」这个产品定的，管理端是工具，不是产品表面：
它应该信息密度高、无动画、系统字体、朴素配色。把梯子搬过去是把手段当成了目的。

## 6. 门槛与顺序

1. §2.2 的数据闸门 + §2.1/2.3/2.4 的三个守卫测试——**在任何页面之前**。
   闸门建在前面，后面写页面的人就不可能违反；建在后面，就要回头审所有页面。
2. 聚合表与 worker 的定时聚合任务——批次 A 的每个数字都从这里来。
3. Jinja2 骨架 + cookie 会话 + CSRF + CSP，只带 A1 登录和 A2 总览的空壳。
4. A3 / A6（队列与健康）——最急用，且完全不碰用户数据。
5. A7 / A8（审计与管理员管理）——端点已有一半。
6. A5（配置与灰度）——需要新建配置表和三态发布流程，独立一轮。
7. A4（记忆质量）——依赖聚合表的记忆维度指标。
8. 批次 B——先定 §4 的脱敏与告知，再动 B3。
